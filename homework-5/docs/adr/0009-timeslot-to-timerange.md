# ADR-0009: Хранить интервал брони спорткомплекса как `TimeRange` / `tstzrange` и мигрировать по паттерну Expand and Contract

| | |
|---|---|
| **Статус** | Accepted |
| **Дата** | 22.10.2026 |
| **Автор** | Леонов Т. А. |
| **Задача** | CAMPUS-110 |
| **Релизы** | v1.9.0 (Expand + Migrate), v1.10.0 (Contract) |
| **Согласовано** | тимлид платформы, DBA |

## Контекст

Модуль «Спортивный комплекс» ИС «Умный кампус» хранит интервал бронирования площадки (зал, бассейн,
корт) в колонке `sports.bookings.time_slot varchar(32)` в виде строки `"2026-11-05 18:00-19:30"`.

Проблемы текущего решения:

1. **Двойное бронирование.** Пересечение интервалов проверяется в коде сравнением строк. Строки не
   сравниваются как время (`"9:00"` > `"18:00"`), а проверка и вставка не атомарны — при
   одновременных запросах одна площадка бронируется дважды (37 обращений в поддержку за сентябрь 2026).
2. **Неоднозначность часового пояса.** В строке нет пояса; мобильное приложение передаёт UTC,
   сайт — местное время, турникеты СК сравнивают со своим временем.
3. **Несколько форматов.** Помимо основного формата в базе есть записи `DD.MM.YYYY HH:MI-HH:MI` из
   старой админ-панели деканата.
4. **Нет индексов по времени.** Поиск свободного окна (CAMPUS-118) и отчёты загрузки требуют
   полного сканирования и разбора строк.

Ограничения: сервис используется 24/7 (турникеты, мобильное приложение), **простой недопустим**;
одновременно с новым API ещё некоторое время будут работать клиенты v1.8 (старые версии мобильного
приложения, прошивка турникетов), которые читают и пишут `timeSlot`.

## Решение

1. **Модель данных.** В C# вводится value object `TimeRange(Start, End)` — полуоткрытый интервал
   `[Start, End)` в UTC с валидацией длительности (15 мин – 4 ч). В PostgreSQL ему соответствует
   встроенный диапазонный тип **`tstzrange`** с границами `'[)'`.
2. **Защита от двойного бронирования на уровне БД** — exclusion constraint
   `EXCLUDE USING gist (facility_id WITH =, time_range WITH &&) WHERE (status = 'Active')`
   (расширение `btree_gist`). До его появления (фаза 3) — `pg_advisory_xact_lock` по площадке в коде.
3. **Миграция по паттерну Expand and Contract**, разнесённая на два релиза:

| Фаза | Скрипт | Релиз | Что происходит | Совместимость |
|---|---|---|---|---|
| 1. Expand | `01_expand.sql` | v1.9.0 | новая колонка `time_range` (NULL), CHECK `NOT VALID`, функции преобразования, триггер синхронизации, GiST-индекс `CONCURRENTLY`; приложение пишет в обе колонки (dual-write) | v1.8 ✔, v1.9 ✔ |
| 2. Migrate | `02_migrate.sql` | v1.9.0 | пакетный backfill (5 000 строк / транзакция, `SKIP LOCKED`), журнал ошибок, проверка, `VALIDATE CONSTRAINT` | v1.8 ✔, v1.9 ✔ |
| 3. Contract | `03_contract.sql` | v1.10.0 | удаление триггера и `time_slot`, `SET NOT NULL`, exclusion constraint | только v1.10+ |

4. **Dual-write в коде + триггер в БД.** Код v1.9 (`NpgsqlBookingRepository.CreateAsync`) явно
   пишет обе колонки — поведение управляется флагом `Migration:WriteLegacyTimeSlot`. Триггер
   `trg_bookings_sync_time_slot` дополнительно покрывает записи от подов v1.8, которые работают
   параллельно во время rolling update, и прямые правки админ-панели.
5. **API** v1.9 принимает `start/end` и устаревший `timeSlot`, в ответе возвращает оба формата.
   Поле `timeSlot` помечено deprecated и удаляется в v1.10.
6. **Наблюдаемость.** Каждый span содержит `jira.issue=CAMPUS-110`, `campus.booking_id`,
   `campus.request.format` (`time_range` / `legacy_time_slot`) — по последнему тегу видно, когда
   все клиенты перешли на новый формат и можно выполнять фазу Contract.

## Рассмотренные альтернативы

| Вариант | Плюсы | Минусы | Итог |
|---|---|---|---|
| **A.** Оставить строку, улучшить разбор в коде | нет миграции | не решает гонку и часовой пояс, нет индекса | ✖ |
| **B.** Две колонки `start_at`, `end_at timestamptz` | привычно, хорошо поддерживается ORM | пересечение — громоздкое условие, нет exclusion constraint «из коробки», нужен CHECK `end_at > start_at` | ✖ |
| **C.** `tstzrange` + exclusion constraint | пересечение (`&&`) и вложенность (`@>`) встроены, GiST-индекс, гарантия отсутствия двойных броней на уровне БД | специфично для PostgreSQL, нужен `btree_gist`, маппинг `NpgsqlRange<DateTime>` | ✔ **выбран** |
| **D.** Миграция «big bang» в одном релизе (`ALTER COLUMN TYPE ... USING`) | быстро в разработке | `ACCESS EXCLUSIVE` блокировка и перезапись таблицы, клиенты v1.8 ломаются сразу, откат только из бэкапа | ✖ |

## Последствия

**Положительные**

* Двойное бронирование невозможно физически (после v1.10.0); до этого — защищено блокировкой.
* Время однозначно (UTC в БД, `+03:00` в API), формат строки больше не важен.
* Поиск свободных слотов и отчёты используют GiST-индекс.
* Релиз v1.9.0 выполняется без простоя и откатывается одной командой `kubectl rollout undo`,
  без отката БД.

**Отрицательные / риски**

* Временное усложнение: две колонки, триггер, флаг конфигурации — до релиза v1.10.0 (~3 недели).
* Записи, которые невозможно разобрать, требуют ручного исправления (журнал
  `sports.bookings_migration_errors`; на тестовых данных — 0 строк после исправления).
* `03_contract.sql` — **точка невозврата** (DROP COLUMN): откат только из бэкапа. Поэтому фаза 3
  выполняется отдельным CR, после 14 дней без запросов в старом формате.
* Код v1.9 читает `time_slot` как fallback, поэтому до выполнения фазы 3 обязательно должен быть
  выкачен v1.10, в котором это чтение удалено.
