## 1. Описание релиза

Сейчас интервал бронирования площадки хранится строкой `time_slot varchar(32)` вида `"2026-11-05 18:00-19:30"`.
Из-за этого:

* БД не может проверить пересечение броней — проверка выполняется в коде строковым сравнением,
  и при одновременных запросах одна площадка бронируется дважды (за сентябрь 2026 — 37 обращений в поддержку);
* нет единого часового пояса: время хранится «как ввели», мобильное приложение и турникеты СК
  трактуют его по-разному;
* в базе встречаются два формата строки (`YYYY-MM-DD` и `DD.MM.YYYY` из старой админ-панели);
* невозможно эффективно искать свободные слоты и строить отчёты загрузки площадок.

Релиз v1.9.0 вводит структуру **`TimeRange`** (в C#) / **`tstzrange`** (в PostgreSQL) и выполняет
**фазы 1–2** паттерна Expand and Contract:

| Компонент | Изменение |
|---|---|
| БД | `01_expand.sql`: колонка `time_range tstzrange`, CHECK-ограничение, триггер синхронизации, GiST-индекс (`CONCURRENTLY`) |
| БД | `02_migrate.sql`: пакетный перенос ~46 тыс. исторических броней, проверка полноты, `VALIDATE CONSTRAINT` |
| API | Dual-write в `time_slot` и `time_range`; приём `start/end` и устаревшего `timeSlot`; ответ содержит оба формата |
| Наблюдаемость | Теги OpenTelemetry `jira.issue=CAMPUS-110`, `campus.booking_id`, `campus.facility_id`, `campus.time_range.*` |
| Тесты | Production Sanity-тест с очисткой тестовой брони |

Фаза 3 (`03_contract.sql`, удаление `time_slot`) **в этот CR не входит** — она оформляется отдельным
CR на релиз v1.10.0 после перевода всех клиентов на новый формат (ориентировочно 18.11.2026).

**Бизнес-цель:** исключить двойное бронирование площадок спорткомплекса (цель — 0 обращений в месяц),
обеспечить корректное время брони во всех клиентах (мобильное приложение, сайт, турникеты),
подготовить основу для функции «поиск свободного окна» (CAMPUS-118).

## 5. План отката (Rollback Plan)

**Критерии отката (любой из):** доля ответов 5xx > 1 % в течение 5 минут; p95 latency > 800 мс;
Sanity-тест упал; `kubectl rollout status` не завершился за 5 минут; ошибки в `02_migrate.sql`,
которые нельзя устранить за 15 минут.

**Решение об откате** принимает релиз-инженер совместно с дежурным SRE. Целевое время отката — **≤ 5 минут**.

| Шаг | Команда | Комментарий |
|---|---|---|
| 1. Откат приложения | `kubectl rollout undo deployment/campus-sports-api -n campus-sports` | возврат на предыдущую ревизию (v1.8.3) |
| 2. Контроль | `kubectl rollout status deployment/campus-sports-api -n campus-sports --timeout=5m` | все поды v1.8.3 `Ready` |
| 3. Проверка | `kubectl rollout history deployment/campus-sports-api -n campus-sports` + smoke-запрос `GET /health/ready` | — |
| 4. БД — ничего не делать | Схема после Expand обратно совместима: v1.8.3 не знает о `time_range`, а триггер продолжает заполнять колонку. Данные в `time_slot` актуальны (dual-write). | откат БД не требуется |
| 5. БД — полный откат (по решению DBA) | `psql -f db/migrations/01_expand_rollback.sql` | только если проблема в самой схеме (например, триггер); удаляет `time_range` |
| 6. Если упал `02_migrate.sql` | Скрипт идемпотентен: исправить строки из `sports.bookings_migration_errors`, перезапустить | приложение при этом работает (fallback-чтение из `time_slot`) |

> ⚠ Точка невозврата наступает только в v1.10.0 при выполнении `03_contract.sql` (DROP COLUMN).
> Для v1.9.0 откат полностью безопасен.

## 6. Оценка влияния и коммуникация

* **Пользователи:** студенты и сотрудники, бронирующие площадки (≈ 4 200 активных); турникеты СК.
* **Ожидаемое влияние:** отсутствует (без простоя). В худшем случае — ошибки создания брони до 5 минут ночью.
* **Коммуникация:** за 24 ч — уведомление в канале `#campus-announcements`; во время работ — `#campus-release`; после — отчёт в CR.
